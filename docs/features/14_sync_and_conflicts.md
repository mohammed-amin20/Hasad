## A. Why this feature exists
Owns the offline-first synchronization pipeline for every module: the durable local outbox, ordered upload, server-side validation/posting acknowledgment, the commit-ordered change feed for downloads, conflict taxonomy and correction flows, permission revocation/expiry handling, and crash recovery. It is a **transport layer, never a validation domain**: every financial effect still occurs only through the posting contracts of features 04–10 executed atomically server-side (I32).

Exclusions: document-specific domain rules and typed rejections (owned by features 04–10, consumed here); encryption/PIN mechanics (D-021, R-05); report semantics (features/12 — freshness labels consumed here).

## B. Roles and user stories
- **Every active member** → creates offline operations, watches the sync queue, corrects rejected operations, pulls changes.
- **`company.settings`/owner** → nothing sync-specific; revocation acts on members via `features/01/02`.
- Forbidden: client-issued official numbers; deleting pending local records without explicit confirmation; advancing a watermark past unpublished rows; reusing a `client_op_id` with different content; bypassing domain validation through the sync path.

## C. Business rules and state transitions
- C1 **Local store:** SQLite encrypted at rest (D-021 OWNER_APPROVED), PIN unlock; contains master-data snapshots, draft rows, the **outbox** and the download watermark. Never an authorization boundary.
- C2 **Outbox states:** `pending → inflight → acked` (terminal) | `rejected` (terminal but correctable) | `held` (permission/dependency hold). Transitions: `pending→inflight` on send; `inflight→acked` on applied ack; `inflight→rejected` on typed domain rejection; `pending/inflight→held` on dependency hold or detected revocation (D-020); `held→pending` when the hold clears; `rejected→(superseded)` when a corrected new op is linked. **Discarding** any un-acked op requires explicit user confirmation and is recorded locally (pre-posting only — the server is never told).
- C3 **Local temporary references:** offline documents carry client UUIDs/ temporary labels only; **official numbers are issued by the server inside the posting transaction** (D-018 OWNER_APPROVED) and arrive in the ack; UI must visually distinguish the two.
- C4 **Upload = one op per `sync_apply` call, strictly per-device FIFO** (RECOMMENDED — keeps per-op commit semantics); the server applies valid synchronized operations **in transaction order** (D-006 OWNER_APPROVED); cross-device order is arrival order serialized by a per-company publication/apply lock (RECOMMENDED_PENDING_VALIDATION).
- C5 **Domain validation is identical to direct RPCs:** `sync_apply` executes the same membership, permission, fiscal-period, mapping, capacity and stock checks as any posting RPC, in the same transaction (I32). Sync is never a validation bypass.
- C6 **Idempotency (corrected design):** `UNIQUE(company_id, client_op_id)` with a **canonical payload hash** (deterministic serialization of the op payload — RECOMMENDED_PENDING_VALIDATION, parity-tested). Rules: op **applied** ⇒ any resend returns the **original committed outcome byte-for-byte** (server id, official number, publication seq); op **rejected** ⇒ resend **re-evaluates** the domain checks (rejections have no business effects, so re-running is safe and prevents permanent blockage from correctable failures such as a reopened period), recording the attempt count; `client_op_id` reused with **different** content ⇒ `IDEMPOTENCY_MISMATCH` (no execution). **Corrections never mutate a sent op:** they are a **new `client_op_id` with an explicit `supersedes_op_id`** link.
- C7 **Rejected-operation evidence (corrected design — survives rollback):** a failed business posting must not be assumed able to commit its own rejection log. Pattern: the business block runs inside a **savepoint-scoped subtransaction**; a typed domain failure rolls back only the subtransaction (discarding all partial business writes); the exception handler then writes the rejection outcome row (`sync_operations.status='rejected'`, error code, attempt) and audit event in the **still-open outer transaction**, which commits normally. Infrastructure failures (connection loss, deadlock) leave **no** committed rejection — the client sees a transport failure and resends; C6 idempotency makes that resend converge (applied or re-evaluated).
- C8 **Dependencies:** each op may declare `depends_on[]` (other `client_op_id`s or referenced local entities). A dependent op whose dependency is not `acked` receives `DEPENDENCY_HELD` and stays `pending` with a visible reason — **never dropped, never silently reordered**. If the dependency lands in `rejected`, dependents are held with the dependency's typed reason; the queue is unblocked only by explicit user action (retry the dependency, supersede it, or discard it with confirmation — discard prompts for the dependent ops).
- C9 **Conflicts taxonomy:** *domain* (stock, capacities, closed period, inactive party/warehouse, `MAPPING_MISSING`) ⇒ typed rejection from features 04–10, corrected offline, retried or superseded; *dependency* ⇒ C8; *draft version* ⇒ stale updates rejected `DRAFT_CONFLICT` — **O27 (REQUIRES_OWNER_DECISION): recommended default = reject stale versions, manual reconciliation, no silent auto-merge**; *authorization* ⇒ C11; *duplicate/replay* ⇒ C6.
- C10 **Download (corrected ordering design — no bigserial/commit-order assumption):** changes become visible to clients only through an explicit **publication mechanism** (I33): business transactions write provisional change rows invisible to clients; a per-company **publication step** (piggybacked on `sync_pull`, executed under an advisory lock) assigns `public_seq` **only to already-committed rows**, monotonically in publication order; clients pull `public_seq > watermark` ranges and advance the watermark only over rows actually received. Because a row becomes visible to publication only after commit and receives its `public_seq` afterward, a later-committing lower-provisional-order row simply receives a **higher** `public_seq` — a client can never advance past a transaction that commits later. Gaps in a client's received seq stream are tolerated (R-04), but the feed itself is contiguous by construction; **periodic snapshots supplement, never replace, the feed** as protection against missed changes. Snapshot resync (`FEED_TRUNCATED` when the watermark predates feed retention) atomically swaps local snapshot + watermark in one local transaction.
- C11 **Authorization (corrected):** membership and permission are checked by the server for **every** `sync_apply`, `sync_pull` and `sync_snapshot` call **including duplicate-ack resends** — a replayed ack never discloses protected data to a revoked or foreign caller (company derived server-side, R-03). After revocation detection the local company data is **locked**; encrypted pending records are **retained** (D-020 OWNER_APPROVED) and cannot be posted until an authorized session restores permission. Offline access expires **24 hours** after the last successful server-side permission verification (D-020); server checks are authoritative regardless of client clocks (server time only).
- C12 **Change-feed durability (corrected):** feed retention is bounded (recommended: ≥ 90 days or a row floor — exact value RECOMMENDED_PENDING_VALIDATION); falling behind triggers `FEED_TRUNCATED` → snapshot resync, **never silent truncation**. Feed rows are included in backup policy (`12_BACKUP_AND_RECOVERY.md`). **Rebuildability is conditional:** regenerating the feed from business tables can reproduce *current entity state at a point* under deterministic ordering, but **not** historical op order — claims are permitted only with verified source data and documented ordering, never asserted unconditionally.
- C13 **Crash recovery:** outbox, watermark, `local_ref_map` and draft state are durable locally; on restart any `inflight` op is re-sent (safe by C6); acks are applied locally transactionally with the entity state they describe; five consecutive failures surface in a visible failed-queue screen with typed Arabic reasons — **recovery never deletes SQLite** (docs/08 requirement).
- C14 **Audit events (mandatory):** `sync.applied` (device id, op id, outcome), `sync.rejected`, `sync.held`, `sync.snapshot_resync`, `sync.discard` (local-only mirror where server-audited), plus every domain event the op triggers in features 04–10.

State chart (outbox): `pending → inflight → acked | rejected`, with `held` reachable from `pending/inflight` and `rejected → superseded`; snapshots: `current → (truncated) → resyncing → current`.

## E. RLS / grants / RPCs
- Private `hasad` schema; RPCs in `hasad_api` INVOKER; privilege model **DRAFT pending the isolated security PoC** (`07`).
- Grants: no direct client write access to `sync_operations`/`sync_changes` (written only by the sync/posting path); `sync_pull`/`sync_snapshot` are read paths scoped by derived membership; **no `anon`**.
- Every call rederives `company_id` from verified membership (R-03); client-supplied company/entity values are filters or consistency checks, never authority. Duplicate-ack resends execute the same membership gate (C11/I32).

## F. Offline SQLite and synchronization
This feature **is** the sync layer. Contract summary (authoritative version lives in `08_OFFLINE_SYNC.md`): encrypted store (D-021) → durable outbox (stable `client_op_id` + idempotency hash) → ordered dependency-aware upload (per-device FIFO) → server validation/posting in transaction order (D-006) → durable ack (C6/C7) → local reconciliation; download via `public_seq` watermark with snapshot supplement (C10); permission lock + 24-h expiry (D-020); visible failed queue; typed Arabic rejection reasons; pending ops excluded from all authoritative figures (D-025 remains OPEN — server-posted-only display recommended, not approved).

## G. Accounting impact (if any)
`No direct posting` from sync itself — it transports domain operations whose accounting effects are defined in features 04–10. Binding invariants: **I31** (exactly-once financial effects under retries), **I32** (no validation bypass), **I33** (feed continuity, watermark safety, pending-excluded-from-totals, convergence). Sync must never create a path that posts a journal entry, movement or payment outside those contracts.

| `sync_status()` | → watermark floor (retention), pending publication count, server time | active member | — |

Typed errors: `IDEMPOTENCY_MISMATCH`, `DEPENDENCY_HELD`, `PERMISSION_DENIED`, `MEMBERSHIP_REQUIRED`, `FEED_TRUNCATED`, plus every domain code from features 04–10. No RPC returns stored outcomes without the membership gate; no RPC accepts a client-issued official number (D-018).

## J. Tests and acceptance criteria
**Positive:** identical resend returns the byte-identical original outcome; resend of a rejected op after the blocking condition is fixed (e.g., period reopened) applies exactly once; out-of-order arrival ⇒ `DEPENDENCY_HELD` then applied after dependency, in order; two devices, last unit ⇒ exactly one applies, the other receives `STOCK_INSUFFICIENT` preserved locally; publication ordering: txn A (provisional order 5) commits after txn B (order 6) — client at watermark over B's `public_seq` still receives A's row on the next pull (gap-injection proof); snapshot resync at `snapshot_seq` + feed continuation converges; crash at each pipeline stage (pre-send, mid-apply, post-apply pre-ack) ⇒ exactly-once posting after restart; revoke-mid-pending ⇒ lock + preserved queue + denied post; 24-h expiry then re-auth restores; rejection row survives its outer commit while the business tables show no partial writes (C7 proof).
**Negative:** `client_op_id` reused with different payload ⇒ `IDEMPOTENCY_MISMATCH` and zero writes; duplicate ack requested by a revoked/foreign caller ⇒ `PERMISSION_DENIED` with no data disclosed; watermark forged/ahead ⇒ pull still returns only own-company rows; op attempting to skip domain validation ⇒ no such path exists (every op runs the full check suite — I32); discarding pending ops without confirmation ⇒ UI-blocked; `anon` everywhere; direct table writes to `sync_operations/sync_changes` ⇒ denied (no grants).
**Concurrency:** parallel resends of one `client_op_id` ⇒ one execution, identical outcomes (row-lock serialization); two-device capacity races (allocations, returns, stock) ⇒ capacities never exceeded; publication lock contention ⇒ no duplicated or skipped `public_seq`.
**Reconciliation/convergence:** Σ applied ops ≡ Σ posted business documents and official numbers exactly once in `doc_numbers`; feed regenerated from business tables under documented ordering ⇒ **state-equivalent** at the snapshot point (conditional rebuildability claim asserted only with verified source data — C12); device after full resync ≡ server state; pending ops excluded from every authoritative total (I33).
Test only disposable datasets (`13_TEST_STRATEGY.md`); database execution belongs to the isolated PoC.
