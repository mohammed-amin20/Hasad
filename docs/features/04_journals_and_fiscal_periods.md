**Source:** V2 clean-slate design (no Hasad V1 reuse). Bound by `15_DECISION_LOG.md` (D-005, D-006, D-013, D-017, D-018, D-019) and the 2026-10-20 accounting planning report.
**Evidence labels:** `PROPOSED` unless marked `OWNER_APPROVED` (by decision ID), `RECOMMENDED_PENDING_VALIDATION`, or `REQUIRES_OWNER_DECISION`.

## A. Why this feature exists
Owns the double-entry general ledger: journal entry headers and lines, balanced atomic posting, fiscal years and monthly periods, strict closing with audited reopening, opening balances, and the linked-reversal correction model. Every other module (sales, purchases, inventory, cash, expenses, payroll) posts **through** this engine via journal line specifications; no module writes finance tables directly (`04_ARCHITECTURE.md` boundary).

Exclusions: business-document semantics (modules 06–11), report layouts (module 12), CoA structure rules (see `features/03`).

## B. Roles and user stories
- **`journals.create` holder** → drafts entries offline/online; drafts are editable and unnumbered.
- **`journals.post` holder** → posts validated entries; official number assigned by the server inside the posting transaction (D-018 OWNER_APPROVED).
- **`journals.reverse` holder** → creates linked reversal entries; never edits/deletes posted history (D-019 OWNER_APPROVED).
- **`fiscal.close` holder** → closes monthly periods; reopening is privileged and audited (D-005 OWNER_APPROVED); recommended owner-only reopening — REQUIRES_OWNER_DECISION (O3).
- **All members** → read entries, trial balance, AR/AP ledgers (derived — D-017 OWNER_APPROVED).
- Forbidden: editing/deleting posted rows; posting into closed periods; supplying document numbers from the client; reversing a reversal.

## C. Business rules and state transitions
- C1 **Entry states:** server-side `draft → posted`. **Pending offline** is a *client outbox* state (D-006 OWNER_APPROVED): the server never holds half-posted journals — sync apply either posts atomically in transaction order or returns a typed rejection preserved locally. **Reversed** is a derived state: a posted entry that any later linked reversal points to (`reversal_of_id`); the original row is never updated. Drafts may be deleted (creator + permission, audited); posted rows never.
- C2 **Balanced double-entry:** Σdebits = Σcredits per entry, enforced by a deferred constraint trigger at COMMIT; each line has exactly one positive side; ≥2 lines per entry. OWNER_APPROVED as a business rule (balanced postings, `02` module 4); trigger mechanism RECOMMENDED_PENDING_VALIDATION.
- C3 **Money:** final amounts `numeric(18,2)` with **HALF_UP** rounding applied at document level (D-005 OWNER_APPROVED). **Intermediate precision** for unit prices, quantities and costing calculations is RECOMMENDED_PENDING_VALIDATION (R-07) — this feature does **not** force 2dp on intermediates. Base currency ILS; single-currency v1 (multi-currency = later phase).
- C4 **Fiscal year:** Jan 1 – Dec 31; **twelve monthly periods** generated by `fiscal_year_create` (D-005 OWNER_APPROVED). Overlapping years rejected.
- C5 **Posting validity:** the entry date must resolve to an **open** period; closed periods reject postings with `PERIOD_CLOSED` (D-005 OWNER_APPROVED). Every posting atomically **rechecks company membership, permission, and period status inside the same server transaction** (approved shared requirements 1, 2, 6).
- C6 **Immutability:** posted headers/lines cannot be updated or deleted — three independent layers: rejecting triggers, absent UPDATE/DELETE grants, RLS draft-only policies (D-019 OWNER_APPROVED; layer mechanism RECOMMENDED_PENDING_VALIDATION).
- C7 **Corrections:** a reversal creates a **new** entry (`entry_kind='reversal'`) with debit↔credit swapped and `reversal_of_id` linking to the original, posted into an **open** period (default current), with mandatory reason + audit. Double reversal ⇒ `ALREADY_REVERSED`. Document-level corrections (credit/debit notes) belong to modules 06/07 and produce their own journals. Linked reversals are the OWNER_APPROVED correction model (D-019).
- C8 **Numbering (wording aligned audit batch 3):** every number is allocated per **company + document type + fiscal year** (D-013 OWNER_APPROVED), restarting annually, **official numbers assigned only by the server** inside the posting transaction under a per-key advisory lock (D-018 OWNER_APPROVED). One shared counter family (`doc_numbers`, D-table below) serves **every** document type — each posted journal entry consumes a number for **its own document type** (e.g., the journal-entry type, plus per-module types via their posting RPCs), and the header `entry_no` is that journal-entry-type number: unique per (company, fiscal_year) **for that type**, never a separate counter. **Counter ownership boundary preserved:** the counter row and its atomic allocation belong to this engine (I8); feature specs configure only how numbers look and when they are issued (`features/13` C7/C8). **Gap claim:** numbers are consumed transactionally (rollback frees them); however this spec does **not** claim gap-free numbering under all failure scenarios (e.g., crash during serialization) without proof — gap policy to be validated in the PoC. RECOMMENDED_PENDING_VALIDATION.
- C9 **Idempotency:** `je_post` accepts an idempotency key (UNIQUE per company); a replay returns the original result without duplicate posting; a reused key with different content ⇒ `IDEMPOTENCY_MISMATCH` (approved shared requirement 13; mechanism RECOMMENDED_PENDING_VALIDATION).
- C10 **Opening balances:** ordinary balanced entries (`entry_kind='opening'`) in period 1, posted only via a dedicated RPC requiring owner permission; year > 1 requires a posted prior-year `closing` entry to link against; `OPENING_EXISTS` prevents duplicates. Every balance remains a sum of posted lines — journal integrity fully preserved (consistent with D-017).
- C11 **Year-end closing workflow (PROPOSED — not owner-approved):** `fiscal_year_close` would generate a balanced `closing` entry (zeroing revenue/expense into retained earnings) and the next year's `opening` entry. Automation itself is REQUIRES_OWNER_DECISION (O2) — no automation is assumed approved.
- C12 **Audit events (mandatory):** `entry.posted`, `entry.reversed`, `entry.draft_deleted`, `period.closed`, `period.reopened`, `year.created`, `year.closed`, `number.issued`, `opening.posted`.

State chart: `draft ⇄ (edit/delete)` → `posted` (immutable, numbered) → derived `reversed` when a linked reversal exists. Periods: `open → closed → (privileged audited reopen) → open`.

## D. Data model (PostgreSQL — proposal until approved)
| Table | Purpose | Tenant scope | Key constraints | Status |
|---|---|---|---|---|
| `fiscal_years` | FY header | `company_id NOT NULL` | `UNIQUE(company_id, start_date)`; Jan1–Dec31 CHECK; `status open/closed` | PROPOSED |
| `fiscal_periods` | 12 monthly periods | `company_id NOT NULL` | `UNIQUE(fiscal_year_id, period_no)`; `period_no CHECK 1..12`; contiguous non-overlapping dates; `status open/closed`; close/reopen stamps + `reopen_count` | PROPOSED |
| `journal_entries` | Headers | `company_id NOT NULL` | `entry_kind standard/opening/closing/reversal/adjustment`; `status draft/posted`; `entry_no` UNIQUE per (company, fiscal_year) — the **journal-entry document-type slice** of the shared `(company, doc_type, fiscal_year)` counter key (D-013); server-issued at posting, never client-supplied; `reversal_of_id` self-FK; `idempotency_key` UNIQUE per company; `posted_at/by` | PROPOSED |
| `journal_lines` | Lines | `company_id NOT NULL` (composite same-company FKs to entry, account, party) | one-sided amount CHECK; `numeric(18,2)` ≥ 0; `line_no` UNIQUE per entry; `party_id` nullable (D-017 subledger dimension) | PROPOSED |
| `doc_numbers` | Server-issued sequences per (company, doc_type, fiscal_year) | `company_id NOT NULL` | PK triple; `next_value`; incremented under advisory lock | PROPOSED |

Deletion policy: posted rows never deleted; drafts deletable with audit. Indexes: `(company_id, entry_no)` unique; `(entry_id)`; `(company_id, account_id)` via join covering; `(reversal_of_id)`; `(company_id, idempotency_key)` unique. Open implementation choices (UUIDv7 site R-08, deferred triggers under transaction pooling, advisory-lock contention) listed in `05_DATABASE_SCHEMA.md`.

## E. RLS / grants / RPCs
- Private `hasad` schema; RPCs in `hasad_api`; INVOKER-only default; the proposed privilege model has **not** passed security testing (see `07_SECURITY_TENANCY_RLS.md` — still DRAFT pending PoC).
- Grants: `SELECT` for `authenticated`; `INSERT` on lines/entries; `UPDATE/DELETE` restricted to drafts via RLS + triggers; no UPDATE/DELETE on posted rows.
- Posting RPCs re-derive identity from `auth.uid()` + live membership; client-supplied company/period/number values are consistency checks only.

## F. Offline SQLite and synchronization
- Drafts may be created offline in the local encrypted store (D-021) and queued in the outbox as **pending** (D-006): server validates, assigns the official number (D-018), and posts **in transaction order**; typed rejections (period closed, permission revoked per D-020, inventory conflict per D-006/D-014) are preserved locally for correction and retry — never discarded.
- Offline documents display temporary local references only; official numbers appear after server approval (D-018 OWNER_APPROVED; UI must distinguish them).
- The client's cached fiscal-period status is UX-only; the server rechecks period status atomically at apply time (C5).

## G. Accounting impact (if any)
This feature **is** the accounting core. Invariants I1–I11 in `09_ACCOUNTING_INVARIANTS.md` bind it. AR/AP derive from posted lines on mapped control accounts per party (D-017 OWNER_APPROVED). VAT posting lines carry the approved D-005 mechanics (optional/configurable VAT, invoice-level inclusive/exclusive, tax grouped by rate with group-total rounding); the actual rate/jurisdiction remains OPEN (D-023) and is not assumed here.

## J. Tests and acceptance criteria
Positive: balanced draft posts and receives number 1 for (company, type, FY); reversal produces swapped linked pair with derived reversed state; close→reopen→re-post works and both transitions are audited; opening entry balances and links to prior-year closing; idempotent replay returns identical entry/number without duplicates; trial balance Σ = 0; AR ledger equals Σ control-account lines per party (D-017 reconciliation).
Negative: unbalanced entry fails at commit and **consumes no number**; post into closed period ⇒ `PERIOD_CLOSED`; post dated outside period bounds; post to parent/inactive/foreign-company account (I5, I9); UPDATE/DELETE on posted rows rejected independently by trigger, grant absence, and RLS; double reversal ⇒ `ALREADY_REVERSED`; reversal while no open period exists ⇒ rejected; concurrent `je_post` calls serialize on the advisory lock — unique numbers, **gap policy observed and recorded (no gap-free claim without proof)**; same idempotency key with different payload ⇒ `IDEMPOTENCY_MISMATCH`; `fiscal_period_reopen` by non-owner ⇒ denied; cross-company entry lines ⇒ composite FK/RLS rejection; `anon` everywhere ⇒ denied.
Reconciliation acceptance (per `09`): realistic month-end sample, returns/credit notes, partial payments, concurrency, reverse + reopen scenario.
Test only disposable datasets (`13_TEST_STRATEGY.md`); database execution belongs to the isolated PoC, not this spec.
