## A. Why this feature exists
Owns company configuration and the **official numbering configuration layer**: legal/business profile, addresses, contacts, optional tax identifiers, the ILS/rounding configuration surface, company VAT toggling, the **effective-dated tax-rate catalogue**, the per-document-type numbering registry (format, issuance point), document templates and Arabic RTL print/branding preferences, settings permissions, audit history, and the configuration lifecycle rules that guarantee settings changes **never rewrite historical posted documents**.

Explicit ownership boundaries (never duplicated here): the **fiscal calendar belongs to `features/04`** (`fiscal_years`/`fiscal_periods` — this feature only projects read-only status and delegates creation); **account-role mappings belong to `features/03`** (`module_account_map` — surfaced only as a completeness dashboard); the **`doc_numbers` counter and its atomic allocation belong to the posting engine contract of `features/04`** (I8) — this feature configures *how numbers look and when they are issued*, never *how the engine counts*.

Exclusions: statutory tax rates, tax IDs and mandatory invoice formats (**D-023 — nothing statutory is invented**); authentication/membership (features/01/02); report layouts (features/12); Storage object disposition (**D-011**).

## B. Roles and user stories
- **Owner / `company.settings` holder** → edits legal/business profile, addresses, contacts, templates and branding.
- **Owner/admin (`company.tax` — recommended mapping, catalogue pending)** → maintains VAT toggle and effective-dated tax-rate versions.
- **Owner-only recommended (`company.numbering` — REQUIRES_OWNER_DECISION adjacency, catalogue pending)** → edits document-type registry (prefix, padding, issuance point). Numbering configuration is business-visible on legal documents, hence the stricter default.
- **All active members** → read settings, format previews, mapping-completeness dashboard; consume cached settings offline (UX only).
- Forbidden: changing ILS/rounding/FY structure through settings RPCs; assigning or reserving official numbers from any settings path; client-supplied `doc_no` anywhere; editing/deleting closed tax-rate versions; deleting settings rows.

## C. Business rules and state transitions
- C1 **Single-row settings core (proposed — RECOMMENDED_PENDING_VALIDATION):** exactly one `company_settings` row per company (PK `company_id`, 1:1 `companies`). Typed columns enforce owner-approved invariants via CHECK constraints (a key-value store could not). A `preferences jsonb` column carries non-critical UI choices only.
- C2 **Profile:** `name_ar`/`name_en` (legal), `display_name` (business), address columns (line/city/region/postal — free text acceptable v1), contact (phone/email/website), optional `tax_id` / `registry_no` stored as **text with no assumed legal-format validation** (D-023-adjacent; consistent with `features/05` C7).
- C3 **Immutable approved constants:** base currency is **CHECK-locked to `ILS`** (OWNER_APPROVED D-005; single-currency v1, multi-currency later-phase); rounding policy (final amounts **2 decimals, HALF_UP**) is **displayed, never editable** — attempts return `SETTING_NOT_CONFIGURABLE`; the fiscal calendar is a read-only projection of `features/04` with edits delegated to `fiscal_year_create` (`SETTING_IMMUTABLE_FISCAL` on any direct attempt).
- C4 **Company VAT configuration (D-005):** `vat_enabled boolean` toggles the whole VAT subsystem. **Per-invoice inclusive/exclusive mode stays a document field, never a company setting** (OWNER_APPROVED: invoice-level choice). VAT off ⇒ tax lines rejected on new documents (`VAT_NOT_CONFIGURED`); history untouched. No rate is ever seeded here (**D-023 OPEN**).
- C5 **Effective-dated tax-rate catalogue (corrected design):** `tax_rates` versions carry `valid_from NOT NULL` / `valid_to NULL` with **boundaries defined once, consistently**: a version applies to documents whose `doc_date` satisfies **`doc_date >= valid_from AND (valid_to IS NULL OR doc_date <= valid_to)`** — `valid_from` inclusive, `valid_to` inclusive; a successor's `valid_from` = predecessor's `valid_to + 1 day`, so windows are disjoint **by construction**; the server additionally rejects any overlap ⇒ `EFFECTIVE_DATE_OVERLAP`. Adding a version appends a row; closing a version sets `valid_to` — **active rows are never mutated once used** (old versions retained forever). Posting resolves the rate in effect **on the document date, server-side** (`RATE_NOT_FOUND_FOR_DATE` when none; `VAT_NOT_CONFIGURED` when VAT is off); the client cache is UX-only. Posted lines keep their **`tax_rate` snapshot forever** (features/06/07) — history never recomputes (safeguard).
- C6 **Document-type registry:** per-company rows (`UNIQUE(company_id, code)`) seeded from a migration-borne global catalogue: Arabic display name, `issuance ∈ {'posting','creation'}`, `format_prefix`, `pad_length CHECK (1..10)`, `is_active`. **Financial documents issue only at successful server posting (D-018 OWNER_APPROVED).** Workflow-document numbering **at creation** (quotes/orders) remains **unresolved under O16** — this spec neither activates nor forbids it; `issuance='creation'` rows stay dormant until O16 answers.
- C7 **Numbering key and format:** the allocation key is `(company_id, doc_type, fiscal_year)` per **D-013 OWNER_APPROVED** (restarting annually); the counter row is `doc_numbers` (owned by `features/04`). Recommended format **`PREFIX-YYYY-NNNN`** (`format_prefix`-`fiscal_year`-zero-padded `pad_length`, default 4) — **RECOMMENDED_PENDING_VALIDATION, O30 (REQUIRES_OWNER_DECISION), NOT owner-approved.** Collisions are prevented across **document types** (separate `doc_type` in the key and in `UNIQUE(company_id, doc_no)`), **fiscal years** (separate key row per FY, restart at 1), and **configuration changes** (a format change applies only to numbers issued afterward; posted `doc_no` strings are immutable; a real format break requires a **new doc-type version/code**, never a counter reset or renumbering).
- C8 **Atomic allocation (engine contract of features/04 — I8):** inside the posting transaction, after all other validation: advisory lock on the key → read/increment `doc_numbers.next_value` → format → write `doc_no` → `number.issued` audit → commit, atomically. **PostgreSQL sequences are deliberately not used** (non-transactional consumption would burn numbers on rollback — RECOMMENDED_PENDING_VALIDATION, pooling contention is a PoC item). **No gap-free claim** until transaction/crash tests pass (I8 position preserved). **Committed numbers are never reassigned.**
- C9 **Failure/retry/offline behavior:** rollback ⇒ the increment rolls back with the transaction — **a failed posting consumes no number**; idempotent replay with the same key and canonical payload returns the original outcome **including the original number, allocating nothing new** (I31; changed payload ⇒ `IDEMPOTENCY_MISMATCH` before allocation); crash before commit ⇒ nothing persisted; crash after commit before ack ⇒ resend returns the same committed number. **Offline:** pending documents receive **no number** — client-side temporary reference `TMP-<first 8 chars of client_op_id>` with a مؤقت badge; it is never written to `doc_no`, never printed as official, and the official number arrives in the server ack (D-018).
- C10 **Templates and printing:** `document_templates` rows (per company, `UNIQUE(company_id, template_code)`, `layout_version`, paper/orientation, header/footer fields, `is_active`). **Templates affect presentation only** — every rendered value (numbers, dates, amounts, tax, parties, official number) comes from immutable posted rows and tenant settings, never from template content; date/number formats follow **tenant settings, not device locale** (`14_UI_ARABIC_RTL_STANDARDS`); logo referenced by **Storage path only** (upload/disposition blocked by **D-011**). **No statutory document format is assumed (D-023).** Template versioning for historical reprints — RECOMMENDED_PENDING_VALIDATION. **`PAYSLIP` template-registry entry (audit batch 3):** payslips render from `features/11` posted run snapshots through a per-company `PAYSLIP` **presentation** template (Arabic RTL, tenant formats — `features/11` C16). A payslip's own reference is a **presentation artifact, not an official financial document number**: the payslip derives its identity from the **posted run's official number + fiscal period + employee** — payslip generation never touches the `doc_numbers` counters and never issues a number of its own. **The distinction between payslip presentation IDs and official financial document numbers is deliberate: no new legally required numbering type is invented or assumed** — any statutory payslip form or number arrives only with D-023/D-024 answers, never from this registry.
- C11 **Historical legal-identity snapshots (unapproved proposal — O31):** recommended default: financial documents snapshot legal identity fields (`legal name`, `tax_id`, `address`) into a `company_snapshot` at posting, so later profile edits never change historical reprints (consistent with tax-snapshot philosophy and the rule *settings never rewrite posted documents*). Alternative (render-from-current-settings) documented, not chosen. **REQUIRES_OWNER_DECISION (O31) — RECOMMENDED_PENDING_VALIDATION.**
- C12 **Settings lifecycle and audit:** settings writes are **online-only** (fresh server authorization; never queued in the outbox — mirrors `features/03` F); every mutation writes exactly one audit event **with old → new values, in the same transaction** via the narrow audit helper: `settings.company_updated`, `settings.tax_rate_added/closed`, `settings.vat_toggled`, `settings.doc_type_updated`, `settings.template_activated/changed`. Rows are updated/deactivated, **never deleted**. Tax versions transition `open → closed` (`valid_to` set); types/templates `active ⇄ inactive` (`DOC_TYPE_IN_USE` blocks deactivating a type with posted documents).

State chart: settings row `updated in place (audited)`; tax versions `active → closed` (append-only successors); doc types/templates `active ⇄ inactive`; documents `draft(TMP ref) → posted(official number)` — the temporary reference is **replaced by**, never converted on an authoritative row.

## E. RLS / grants / RPCs
- Private `hasad` schema; RPCs in `hasad_api` **INVOKER**, pinned `search_path`; `EXECUTE` revoked from `PUBLIC`/`anon`. **The INVOKER/RLS privilege model is DRAFT — not verified** (`07_SECURITY_TENANCY_RLS.md`, pending the isolated security PoC).
- Grants: reads for any active member; writes only through RPCs gated by `company.settings` / `company.tax` / `company.numbering` (recommended mappings above — final mapping joins the **owner-pending role catalogue** in `features/02`); **no direct client write grants** on `doc_numbers` (counter written only by posting RPCs), tax versions, or settings rows beyond their RPCs.
- Every RPC rederives company from live membership server-side (R-03); client-supplied `company_id`/`doc_no`/rate values are consistency inputs, never trusted; **no settings RPC accepts or issues an official number** — `doc_number_format_preview` returns the **format mask only** and reserves nothing.

## F. Offline SQLite and synchronization
- Settings, tax-rate catalogue, doc-type formats and templates are **cached read-only** for offline drafting (UX only); the server re-validates everything at posting (rate-by-date, VAT toggle, format, mapping completeness).
- **Settings mutations are online-only** — never entered in the outbox (fresh-authorization class, mirroring CoA edits); no conflict policy is needed because clients cannot stage settings changes.
- **Temporary references (D-018):** offline drafts carry `TMP-<8 chars>` only; on sync the server posts in transaction order (D-006) and returns the official number in the ack; the client replaces the temporary badge transactionally with the entity state; rejected operations keep their temporary reference for correction.
- Cached format previews and VAT status age with the normal freshness labels (watermark/server time, `08_OFFLINE_SYNC.md`); they never gate security.

## G. Accounting impact (if any)

## J. Tests and acceptance criteria
**Positive:** first settings write creates the 1:1 row; profile update writes exactly one audit row with old→new values; rate add → close → successor with boundaries `valid_to + 1 day` resolve correctly — a document dated inside an old window uses the **old** rate even after two later versions exist (snapshot proof); VAT toggle off ⇒ new documents reject tax lines while history renders unchanged; format preview displays the mask **without consuming any counter value**; 500 postings on one `(company, type, FY)` key ⇒ 500 unique consecutive numbers, Σ `number.issued` = 500; offline draft with `TMP-…` syncs and receives its official number **exactly once**, badge replaced; profile legal-name change ⇒ new documents carry the new identity while old reprints are unchanged (O31 default behavior).
**Negative:** set currency ≠ ILS or rounding ≠ 2dp/HALF_UP ⇒ `SETTING_NOT_CONFIGURABLE`; direct fiscal-calendar write ⇒ `SETTING_IMMUTABLE_FISCAL`; overlapping rate windows for the same `(company, code)` ⇒ `EFFECTIVE_DATE_OVERLAP`; document dated with no effective version ⇒ `RATE_NOT_FOUND_FOR_DATE`; posting while VAT off with a tax line ⇒ `VAT_NOT_CONFIGURED`; **client-supplied `doc_no` rejected by every posting RPC (structural test across 04/06/07/09/10)**; pending offline document attempting to persist any number-like value in `doc_no` ⇒ impossible (server-written column); `TMP-…` printed as an official number ⇒ UI/structure test failure; deactivate a doc type with posted documents ⇒ `DOC_TYPE_IN_USE`; mutating a closed/used rate version ⇒ rejected; cross-company settings/rate/type/template refs ⇒ composite FK/RLS rejection; non-privileged member calling `doc_type_config_update`/`tax_rate_add` ⇒ `PERMISSION_DENIED`; format change mid-year renumbers nothing (existing rows untouched); `anon` everywhere ⇒ denied; direct writes to `doc_numbers` ⇒ no grants.
**Concurrency:** N simultaneous posts on one key ⇒ serialized on the advisory lock — unique consecutive numbers, no lost updates, single counter row; posts on **different types/FYs in parallel** ⇒ no cross-blocking (collision-separation proof across types and years); concurrent `tax_rate_add` + `tax_rate_close` ⇒ serialized, windows never overlap; **forced failure after increment ⇒ counter unchanged (rollback consumes no number)**; duplicate idempotent replay ⇒ same number returned, **zero new allocation** (changed payload ⇒ `IDEMPOTENCY_MISMATCH` before allocation); crash-post-commit replay ⇒ original number (I31).
**Reconciliation:** Σ `number.issued` audit rows ≡ count of posted documents with numbers per (company, type, FY); counter `next_value` ≡ max issued + 1 for the key; rate-resolution results ≡ posted `tax_rate` snapshots on sampled documents; no gap-free assertion is made — gaps, if any under crash injection, are **observed and recorded** (I8). Test only disposable datasets (`13_TEST_STRATEGY.md`); database execution belongs to the isolated PoC.
